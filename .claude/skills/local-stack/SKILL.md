# Local stack run modes

- **Hybrid (dev)** — `docker compose up -d` for backing services + `pnpm --filter ... dev` for api/web/worker outside the container. Uses `apps/<app>/.env` (copy from `.env.example`).
- **Docker-only (VM / prod-like)** — `make setup && make up`. All env values live in a **single root `.env`** sectioned per service (`infra/env.template` is the canonical layout). The web image carries no `NEXT_PUBLIC_*` values, so an env-only VM redeploy is a plain `docker compose up -d` — rebuild only when code changed. The base `docker-compose.yml` is the prod/VM posture: TLS verify **on**, `INSTANCE_ENV=production`, no host-published DB/Redis/MinIO ports, and MinIO behind the **`storage`** compose profile. `make up` / `stack:up` layer `docker-compose.dev.yml`, which rebinds those ports to `127.0.0.1`, sets `INSTANCE_ENV=development`, and relaxes TLS for the local CA. api/worker run an `assertTlsPosture` startup guard that hard-fails boot when TLS verification is off under a production `INSTANCE_ENV`.
- **Unified full-ecosystem stack (`local-setup/`)** — brings up **both** aggregator-dpg _and_ the upstream signals-dpg (+ shared Postgres/Redis/Keycloak/MinIO/Mailpit) in one `docker compose up -d`, wired for localhost. It builds both repos, so it expects `aggregator-dpg` and `signals-dpg` checked out as **siblings** and is run from `local-setup/`. See `local-setup/LOCAL_SETUP.md` for the full walkthrough (Track A = all-in-Docker, Track B = hybrid). **signals-search is an add-on file**: `docker compose -f docker-compose.search.yml up -d` (it includes `docker-compose.yml`) (LOCAL_SETUP.md §10): a query API on host **3110** (not 3100 — the portal owns that), an ingestion worker and a TEI embedding server, pulled prebuilt from public GHCR. The embedder wants 3-4 GB, so budget ≥10 GB of Docker memory with search (≈6 GB without). aggregator → signals uses a Keycloak client-credentials token (`SIGNALSTACK_AUTH_MODE=bearer`, client `aggregator-dpg`); signals → search uses the `signals-search` apikey `SIGNALS_SEARCH_API_KEY` (generated by `gen-secrets.sh`, seeded by `signals-bootstrap`), so nothing is copied from seed output. The compose here (repo root `docker-compose.yml`) remains the VM/prod nginx+certbot ingress variant.

## RBAC edge (Envoy + OPA)

Route permissions are decided by an Envoy + OPA edge in front of the API, not by the API (`docs/rbac/rbac-edge-enforcement.md`). Both compose stacks run it: `envoy` (`aggregator-envoy` in the root stack, `sd-aggregator-envoy` in `local-setup/`, which owns host port 4000) forwards to the API only what OPA allows, and nginx `/backend/` and the web app reach the API through it (`API_BASE_URL=http://envoy:4000` in the root stack). `RBAC_MODE` is the one switch for both: the root stack defaults to `log`, `local-setup/` to `enforce`.

- **Logs.** Every request is one Envoy access-log line, `operation: rbac.edge` with `outcome` `allow` / `would_deny` / `deny` and the `permission` the route needs. Its `request_id` is the API's `reqId`, so a request refused at the edge has no API log line at all.
- **An existing `.env` with `API_BASE_URL=http://api:4000` bypasses the edge.** `infra/env.template` and `infra/env.local` now say `http://envoy:4000`; copy that into any `.env` made before.
- **OPA down refuses everything**, public routes included (fail closed). After OPA restarts, permission routes come back within one catalogue refresh (30 s), when the API pushes the role catalogue again.
- **The API run on the host (`pnpm dev`) has no edge**, so requests reach it directly. Keep it on `RBAC_MODE=log` or `off`; never `enforce`.
- `infra/envoy/envoy.yaml` is a template: each stack fills in the API hostname, the token issuer and the JWKS URL at start. The root stack's issuer is the public `…/auth/realms/<realm>`, the one the API expects.

## Deploying to a VM

Replace `localhost` and `keycloak` everywhere in `.env` with the VM hostname/IP, and update the `aggregator-portal` client's **Valid Redirect URIs** + **Web Origins** in the Keycloak admin console.

**`CONFIG_ROOT` must resolve, or the API will not boot.** Email copy is read from `config/emails/messages.properties` at startup and validated for completeness, so a wrong `CONFIG_ROOT` — or a bind mount shadowing the image's own `config/` copy with an incomplete tree — crash-loops the container instead of failing one endpoint. That is deliberate (blank emails are worse than a loud stop), but it makes the config path a boot dependency rather than a request-path one. The error names the file and the variable: `email copy defaults not found at <path> — check CONFIG_ROOT and that config/ is present`. Same class of mistake as a stale `AGGREGATOR_CONFIG_PATH`, with a wider blast radius.

## Stack commands

`make setup` is a one-shot that copies `infra/env.template` → `.env` (chmod 600) and adds `127.0.0.1 keycloak` to `/etc/hosts`. `pnpm stack:setup` / `stack:up` are the cross-platform equivalents (Windows-friendly; `make` not required), and the same script covers `stack:down | stack:reset | stack:logs | stack:ps | stack:psql | stack:rebuild-web`.

Two that bite if you skip them:

- `make reset` runs `docker compose down -v` — **DESTROYS data volumes**.
- `make rebuild-web` rebuilds the web image and restarts the container — needed after web **code** changes only. Env changes (`ENABLED_LANGUAGES`, `INVITE_MAX_RECIPIENTS`, …) are read at runtime, so a restart is enough; the image deliberately takes no `NEXT_PUBLIC_*` build args.
- `make rebuild-keycloak` rebuilds the OTP SPI jar and restarts Keycloak.
