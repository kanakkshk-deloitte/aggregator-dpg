# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository

Aggregator DPG — the Aggregator-facing app of the Blue Dots / Signal Stack ecosystem. pnpm + Turbo monorepo, TypeScript-only. See `README.md` for the product spec and `SETUP.md` for the local-stack walkthrough.

## Toolchain

Versions and ports are in `package.json` (`engines`, `packageManager`), `turbo.json`, and `docker-compose.yml`. Two things those files don't tell you:

- **pnpm is required** — other package managers are not supported.
- **AWS S3** is **not** in compose — in the VM/prod posture the API and worker hit real S3 via IAM role / `~/.aws/credentials`. For local dev, object storage is a **MinIO** container behind the `storage` compose profile (started by the dev overlay); see the Local stack run modes note below.

## Common commands

Root `package.json` scripts cover the whole-repo tasks (`pnpm -w build|test|lint|typecheck`, `pnpm dep-check`) and the `stack:*` wrappers; each app/package `package.json` covers its own `dev`/`test`/`db:*`. `Makefile` covers the container targets. The non-obvious ones:

```bash
pnpm --filter <pkg> test -- path/to/file.test.ts   # single test file
pnpm --filter <pkg> test -- -t "test name"         # single test by name
pnpm --filter <pkg> test --coverage                # ≥ 70% line target
```

Stack run modes, env layout, and the VM-deploy checklist live in the `local-stack` skill — including the footgun that `make reset` destroys data volumes. Note `make rebuild-web` is only needed for web **code** changes: the web image takes no `NEXT_PUBLIC_*` build args, so env changes apply on restart (see `apps/web/CLAUDE.md` for the server-resolve-then-pass-down pattern that keeps it that way).

Commits run husky/lint-staged (`prettier --write` + `eslint --fix`) on staged files. Conventional Commits required; **do not bypass with `--no-verify`** (per `CONTRIBUTING.md`).

## Architecture

### Three deployable apps (`apps/`)

- **`api`** — Fastify BFF on `:4000`. Owns the Aggregator DB (Drizzle + Postgres), Keycloak admin integration, registration/approval flow, bulk-upload entry point, registration links, profile endpoints. Coordinator and org-owner name / email / phone are stored once in a `contact` table (#825, migrations 0025/0026) referenced by `contact_id` — see `apps/api/CLAUDE.md` and, for existing instances, `docs/contact-migration-runbook.md`. Reads upstream Signal Stack (UBI backend) and Jobs Stack; in MVP it has **no write access** to Signal Stack except via the bulk-create paths. Every handler asserts `session.aggregator_id`; `aggregator_id` is **never** trusted from the client. Registration is an in-app **token-based email-approval** flow (signed approval-token links → approver page → atomic CAS on the row → Keycloak user enable/role assign), with expired-link regenerate, resubmit-reclaim, and a service-auth stale-registration prune endpoint. Registration also records an append-only **consent ledger** row in the same transaction as the account (fail-closed: no subject is provisioned without a consent record; the ledger is the only home of consent since migration 0029). Every coordinator belongs to an **organisation** (`organisations`, always on since migration 0028) — see below. Also exposes **contact-support** endpoints (`GET /v1/support/config`, `POST /v1/support`, both authenticated) gated by the per-instance **`SUPPORT_EMAIL`** env: unset ⇒ config reports `enabled:false` and `POST` returns `503 SUPPORT_NOT_CONFIGURED`; set ⇒ the submission is emailed via the aggregator's own mailer (`getMailer()`) with Reply-To = the submitting coordinator (a failed send is `502 SUPPORT_SEND_FAILED`). The form accepts optional image/video/audio **attachments** (base64 `{filename,contentType,data}`, server-side MIME allowlist + filename sanitisation, up to `SUPPORT_ATTACHMENT_MAX_FILES` files / `SUPPORT_ATTACHMENT_MAX_TOTAL_BYTES` decoded bytes, per-coordinator rate-limited); the SES adapter sends attachment-bearing mail as raw MIME (`Content.Raw` via nodemailer `MailComposer`) while the no-attachment path stays `Content.Simple`. The participant dashboard (`GET /v1/dashboard/items`) returns **draft + live** profiles only by default — paused/retired are excluded; `?lifecycle=draft|live|paused|account_only` narrows to one bucket and `meta.tiles` still counts the full dataset (#562). A **campaign-manager** subsystem drives outbound/export flows on a durable async-job engine (one `campaign_job` row per request, enqueued to the worker and polled for per-item status): `POST /v1/campaign/export` + `GET /v1/campaign/export/{job_id}` (participant PII export, #579), `POST /v1/campaign/voice` + `GET /v1/campaign/voice/{job_id}` (Raya voice-call dispatch, #577), each also listable (`GET /v1/campaign/{channel}` cursor-paged, org- and channel-scoped). The channel work itself runs in the worker's `campaign` role.
- **`web`** — Next.js 15 (App Router) portal + its own BFF. Anonymous flows hit the backend with a service-account token (`service-token.ts`); authenticated flows attach the user OIDC token via `callApi` (`upstream-client.ts`). Sessions are signed cookies backed by Redis (`lib/session/`). Forms are RJSF-driven from `config/schemas/aggregator/*.json` so non-engineers can evolve the profile/registration forms without code changes. Registration renders the coordinator form with its organisation selector (owner registration is the `/register/owner` deep link), with a required consent checkbox and a read-only Terms/Privacy popup (`components/consent/`) whose Markdown content is loaded from `config/**/consent.json`. The `/profile` page renders that **same** `registration.v1` schema **read-only** (single source via `lib/aggregator-schema.server.ts`, every field disabled) with a stubbed "Request an update" panel over the `x-updatable` fields — never an editable profile form. The Sidebar's "Contact support" entry appears only when the API reports `SUPPORT_EMAIL` configured (`GET /v1/support/config`, surfaced via `supportEnabled` on `auth-context`). The schema-driven forms render three **custom RJSF widgets** (#778): address autocomplete (single + multi) backed by a pluggable geo provider — Google Places when `GOOGLE_MAPS_API_KEY` is set, the key-less Photon geocoder otherwise — and a reference/institute picker reading `colleges-<region>.json` from `REFERENCE_BASE_URL`. Their configuration is resolved **server-side** and published through `FormRuntimeConfigProvider`, never `NEXT_PUBLIC_*`; the datasets are **not** committed here (see `apps/web/CLAUDE.md`). With no `REFERENCE_BASE_URL` the reference picker degrades to a plain text input, which is the behaviour that predates the feature — but the **address** widgets do not: with no `GOOGLE_MAPS_API_KEY` they fall back to the **public** Photon endpoint (`https://photon.komoot.io`), so in the default configuration every keystroke in an address field reaches a third party. A deployment that cannot accept that must set a maps key or point `photonUrl` at its own instance.

- **`worker`** — BullMQ jobs (`bulk-file-process`, `bulk-row-process`, `bulk-finalise`, `cron-watchdog`, `link-metrics-rollup`, `campaign-process`). Consumes the same DB schema + S3 + signalstack-writer. Crontab-style jobs are watchdogged. Bulk CSV parsing is **streamed** (`bulk-file-stream`) to bound memory on large files. The `campaign-process` consumer (worker's `campaign` role) runs the unified campaign async-job pipeline — one `campaign_job` row at a time, dispatching the per-channel handler (export / voice today) and writing item + job status back. A process runs every consumer role by default; set `WORKER_ROLES` (comma-separated subset of `file,row,finalise,cron,campaign`, or `all`) to split roles across pods — e.g. run the CPU-heavy `file` parser in its own deployment. The union of roles across the fleet must cover all five or uploads/campaigns strand.

### Shared packages (`packages/`)

All cross-package consumption goes through **subpath exports** declared in each `package.json`. Common pattern: every service package exports `./interface` (abstract class + Zod schemas), one or more concrete impls (`./postgres`, `./http`, `./memory`), and `./testing` (in-memory fake + `buildX()` helpers). Apps and other packages import from `./interface` and `./testing` only.

- **`shared-primitives`** — `Result<T, E>` (`ok` / `err` / `match`), typed error hierarchy (`BaseError` → `UpstreamError`, `ConfigError`, `AuthError`, `ValidationError`, `DomainError`), branded IDs, shared DTOs (`Filter`, `Paginated<T>`, `Timestamps`), Beckn primitives, aggregator-specific DTOs.
- **`db-schema`** — Drizzle table definitions and inferred types. The single source of truth for the schema; apps import tables from here.
- **`signalstack-writer`** — abstract base + HTTP impl + in-memory fake, shared by the API and worker. (A sibling `participants-writer` package existed until the local `participants` mirror was dropped in migration 0024; Signals is now the sole store of record for participants.) `signalstack-writer` also exposes `fetchDecryptedProfiles` (backs the server-side profile-data CSV export). Its `onboard` call also forwards optional `item_locations` — coordinates the registrant picked from the address autocomplete — so signals stores the picked point instead of re-geocoding the address text (#778). **Auth to Signals is `SIGNALSTACK_AUTH_MODE`-selected: `apikey` (default) sends `SIGNALSTACK_ADMIN_KEY` as `x-api-key`; `bearer` mints a Keycloak client-credentials token via `KeycloakClientCredentialsTokenProvider` instead (requires `SIGNALSTACK_CLIENT_ID`/`_SECRET` + `KEYCLOAK_URL`/`_REALM`, and `SIGNALSTACK_CLIENT_ID` must equal this aggregator's Signals `organization.slug`, asserted at boot).** The SignalStack env fields, the TLS-posture guard, and the client-identity assertion are shared by the api + worker via `@aggregator-dpg/shared-primitives/config` (spread into each `ConfigSchema` so the two processes can't drift).
- **`consent-ledger`** — append-only registration-consent store. Abstract `ConsentLedgerBase` (`./interface`) + `./postgres` / `./memory` / `./testing`; `recordRegistrationConsent` writes a `consent_record` row for a `user` or an `organisation` (typed `user_id` / `org_id` link, `valid_till`) and never throws (`Result<T, BaseError>`); `withExecutor(tx)` binds it to the caller's transaction, which is how registration writes consent in the same transaction as the account (migration 0029). The ledger is the only home of consent and is append-only (a database trigger).
- **`queue`** — BullMQ wiring (queue names, types, connection helpers).
- **`schema-loader`** / **`config-loader`** / **`schema-service`** — config-as-code loaders. Domain/env-specific values come from `config/*.yaml` and `config/schemas/`, **never** hardcoded. `config-loader` also exposes a `./consent` subpath that loads + validates per-audience (`org` / `aggregator`) versioned consent content (`consent.json`), resolved by `AGGREGATOR_NETWORK` / `AGGREGATOR_BRAND` with brand override merge. The consent loader renders the `__SUPPORT_EMAIL__` placeholder in that content to `CONSENT_SUPPORT_EMAIL` (default `hello@bluedotseconomy.org`) at load, so the T&C/Privacy/Grievances contact is deploy-time configurable without editing consent content (#266) — distinct from `SUPPORT_EMAIL` (the contact-form recipient).
- **`network-config`** — per-deployment binding that lets the aggregator run against ANY signalstack network (blue_dot, purple_dot, …) with no hardcoded domain ids / item types / field names. `NetworkConfigLoader` contract (`./interface`) + `./loader` / `./sniffer` / `./paths` / `./testing`, plus `./signals-cta` — the single shared `signals_cta` default rule that both the api and the web client import so the Signals hand-off flag can't drift between the two. Two more shared rules live alongside it (#904): `./uri-fields` (Signals' `URL_PATTERN`, copied verbatim, and `applyUrlRule`, which the loader applies so every `x-uri` and `format: "uri"` field validates exactly as Signals does — scheme optional) and `./field-errors` (Signals' per-field error wording, so the public form and bulk `errors.csv` name the field and never show a raw regex). The brand block also carries an optional `attribution` array (`{label, name, logo?}`, signals-dpg#720) — **opt-in per brand**: only a `brand.json` that declares it changes the `/v1/aggregator-config` payload, so every other deployment is byte-identical to before.
- **`mailer`** — vendor-neutral email adapter shared by the api + worker. `MailerAdapter` contract (`./interface`) with SMTP (default; dev MailHog / customer SMTP) and AWS SES impls chosen by `MAIL_PROVIDER`; `getMailer()` returns a process-wide singleton so the SMTP pool is reused. Attachment-bearing mail is sent as raw MIME; `./testing` provides an in-memory fake.
- **`voice-provider`** — provider-agnostic egress port for the campaign voice channel. `VoiceProviderBase` (`./interface`) with a concrete Raya impl + `./testing`; the worker's `campaign` voice handler dispatches through it behind a **fail-closed** Redis egress gate that bounds our outbound call rate against the provider's budget (unlike the api's fail-open public-submit limiter).
- **`profile-csv`** — server-side CSV builder for the "Export profile data" action. Turns decrypted signalstack profiles into an RFC-4180 CSV (identity columns — name, then phone/mobile — first, remaining `item_state` keys alphabetical), every value neutralised against spreadsheet formula injection. Single default export, no subpaths.
- **`tsconfig`** — `base.json`, `node.json`, `next.json` extends-targets.
- **`_template`** — copy-paste scaffold for a new service package (interface + memory + testing).

### Identity / OIDC

Keycloak realm `bluedots` (imported on first boot from `infra/keycloak/realms/realm.json`). Three confidential clients: `aggregator-portal` (web, OIDC code flow + PKCE), `aggregator-api` (apps/api admin ops, service account), and `aggregator-bff` (web BFF anonymous-proxy service account). The `aggregator-api` service account holds `realm-management` roles `manage-users` (user CRUD + role mapping) **and** `manage-realm` (group create/manage for the org hierarchy); `aggregator-bff` holds **no** realm-management roles — it only mints a service-account token to call the aggregator API, so a BFF-secret leak cannot administer the realm (the BFF must never reuse the `aggregator-api` client). Client secrets are **not** committed in the realm JSON — `render-realm.sh` substitutes `__AGGREGATOR_{API,PORTAL,BFF}_SECRET__` from `KEYCLOAK_ADMIN_CLIENT_SECRET` / `OIDC_CLIENT_SECRET` / `BFF_SERVICE_CLIENT_SECRET` at container boot and fails hard if any is unset. The realm ships an `org_owner` realm role (required on every instance); it is assigned to an org owner at org approval (and by `train enable-owners` for owners approved before Phase 5), and the portal gate admits it. A custom OTP-by-email/phone authenticator SPI is bundled at `infra/keycloak/providers/keycloak-otp-1.0.0-SNAPSHOT.jar` and rebuilt from <https://github.com/sanketika-labs/keycloak-otp-authenticator> — this copy is **local-dev only** (Compose bind-mounts it into the stock Keycloak image, and `start-dev` re-indexes providers on every boot). The **deployment** Keycloak image — the same SPI baked in with `kc.sh build` pre-run — is built in the **bluedots-automation** repo at `dockerfiles/keycloak/` and published as `ghcr.io/<owner>/keycloak-server`; Keycloak is a shared common service for both DPGs, so its image and its deployment realm are owned there, not here. Nothing in `infra/keycloak/` is upstream of that: treat the two as independent (see `scripts/build-realm.sh` in that repo). The per-network **login theme** image is still built here (`infra/keycloak/themes.Dockerfile`, `build-theme-image.sh`, `keycloak-theme-build.yaml`), because its brand strings come from this repo's `config/<network>[/<brand>]/keycloak.env`. A post-import init script (`infra/keycloak/init/apply-user-profile.sh`) enables unmanaged attributes + applies SMTP config, and declares `aggregator_id`, `decision_made`, `aggregator_type`, `signalstack_org_id` and `roles` **admin-only** (they drive the portal gate and the token claims the apps and the RBAC edge act on, and are written only by the API's service account; the boot fails if they are not admin-only). `roles` is multivalued and mapped into the access token, where the Envoy + OPA edge reads it (`docs/rbac/rbac-edge-enforcement.md`); the same `keycloak-init` sidecar then runs `apply-portal-gate.py`, which reconciles the `aggregator-portal` entitlement gate over the admin REST API on every boot (realm import only applies to an empty realm). The gate denies a user who has neither an `aggregator_id` nor the `org_owner` role, and a coordinator whose `decision_made` is not `approved`; the same change must reach the deployment realm in bluedots-automation. That script is verify-first (its verifier is unit-tested in `infra/keycloak/init/test_apply_portal_gate.py`, and an older gate fails it and is rebuilt) — a no-op when the gate is already correct — and fail-closed: it builds and verifies the replacement flow tree before rebinding the client, and on any failure restores the previous binding, prints `GATE NOT APPLIED`, and exits non-zero rather than leaving the portal on the ungated default browser flow. Two protocol mappers (`aggregator_id`, `phone_number` user attributes → token claims) **must be added by hand** after a fresh import — see `SETUP.md` §5; without them the profile endpoint returns `403 MISSING_AGGREGATOR_ID`. Token verification is issuer-scoped **plus** client-scoped — `access-token.ts` enforces an `azp` allow-list (`KEYCLOAK_ALLOWED_AZP`, default `aggregator-portal,aggregator-api,aggregator-bff`) on both the user and service-account paths, plus an opt-in audience check (`KEYCLOAK_EXPECTED_AUDIENCE`, which needs the realm `oidc-audience-mapper`); both no-op when unset.

### Organisations (always on since migration 0028)

`aggregator_orgs` became `organisations` and the `ORG_HIERARCHY_ENABLED` flag is gone. There is exactly one `network_facilitator` org (the root) and every other org is an `aggregator` org under it — directly, or under another active aggregator org picked at registration (`parent_id`), within the instance's depth, children and total-org limits (`docs/org-hierarchy.md`) — including a fixed **Default** org (`slug = 'default'`) that holds coordinators with no other org — formerly-flat instances keep their flow through it. The root's slug / name / owner are placeholders in the migration and are reconciled from config at every boot (`services/organisation-root.ts`: `brand.url_slug`, the network name, the first `ADMIN_EMAILS`; the Default org's owner is the optional `DEFAULT_ORG_OWNER_EMAIL`). The API exposes `/v1/orgs*` (create/list) and `/admin/v1/orgs*` (approval by emailed link); a real org is its own registration+approval flow (mirrored Keycloak group, disabled org-owner user enabled + granted `org_owner` + added to the group at approval). Since Phase 5 org owners and the network admin (the root's owner) **sign in** to the same portal and use the console APIs `/v1/user/*` and `/v1/org/*` (decide coordinators and orgs, invite; out of reach answers 404). Reach is one level down for everyone, the network admin included: an owner sees its own orgs and, view-only, their direct children (the network admin, which owns the root, sees the top-level orgs); nothing deeper is visible, and coordinators are visible only in the orgs one owns. A new org's review email goes to its parent org's owner (`ADMIN_EMAILS` for a top-level org), who alone approves or rejects it (every Org Admin holds `orgs.onboard` since migration 0035); a rejection needs a reason. An org's details, name included, are edited by its owner only; the network admin sees them read-only. An org's `known_as` is set by the owner of its parent (the network admin for a top-level org), from the parent's own list of values (table `org_known_as`, one row per org; `known_as_values` on the wire) — see `apps/api/CLAUDE.md` and, for the RBAC work that builds on it, `docs/plans/phase-5-rbac-handoff.md`. Coordinator registration takes `org_id` (or an invite), stored in `users.org_id`; the approval token always carries that org, and the review email goes to the org owner (Default: `DEFAULT_ORG_OWNER_EMAIL`, else `ADMIN_EMAILS`). The token↔org binding is enforced on the decision path. `url`, `locations`, company and GST belong to the org and are rendered for its coordinators, falling back to the coordinator's own values (`users.legacy_org_details`); see `apps/api/CLAUDE.md`.

## Project rules (`.claude/rules/`)

Non-negotiable for any code change. Some load always; some are path-scoped and only enter context when you touch a matching file (frontmatter `paths:` — see each file):

- **`error-handling.md`**, **`logging-observability.md`**, **`configuration-discipline.md`**, **`code-documentation.md`** — **always loaded**, genuinely repo-wide (external-call timeouts/retry/typed errors; structured pino logging; no hardcoded domain/env values; TSDoc on every public API).
- **`pull-requests.md`** — **always loaded**. One PR per block (api, worker, web, infra/config), with package and doc changes in the PR of the block they belong to, linked as a GitHub stack with `gh stack`; a combined PR only for a small change and only with the user's explicit approval; CI started by hand on stacked PRs.
- **`base-class-pattern.md`** + **`interfaces.md`** — **path-scoped** to `packages/*/src/**`, `apps/api/src/services/**`, `apps/web/src/lib/{oidc,session}/**` (the only places this repo authors an `interface.ts`-style abstract-class contract — `apps/worker` never does). Every cross-package contract is an `abstract class` (NOT a TS `interface`), schema/DTO naming (`<Entity>Schema`, `Create<Entity>Input`, etc.), `Result<T, BaseError>` returns, never throw across a service boundary.
- **`testing.md`** — **path-scoped** to `packages/*/src/testing.ts`, `packages/*/src/testing/**`, `apps/api/src/services/**` (wherever the `./testing` fake-subpath convention actually lives). Fakes over `vi.mock()`, extend the in-memory impl, `seed()` + `build<Entity>()` helpers.
- **`testing-requirements.md`** — **path-scoped** to any test file (`**/*.test.ts(x)`, `**/*.integration.test.ts`, `**/__tests__/**`) — applies repo-wide including `apps/web`/`apps/worker` tests that don't use the fake-subpath convention. Vitest only, ≥70% line coverage, `.integration.test.ts` excluded from `pnpm -w test`.
- **`typescript-style.md`** — **path-scoped** to `**/*.ts(x)`. Language baseline: no `any`, no `as` casts (validate with Zod), `===`, string-literal unions over `enum`, discriminated unions over optional-field piles, `Promise.all` for independent calls, named exports. It defers to `interfaces.md` on service contracts (abstract class, not `interface`) and to `error-handling.md` on `Result` vs throwing.
- **`react-components.md`** — **path-scoped** to `apps/web/src/**/*.tsx` and `apps/web/src/hooks/**`. Component size, stable list keys, no state mutation, functional setters, derive-don't-mirror, minimal effects with cleanup, and no data fetching in `useEffect`.
- **`nextjs-app-router.md`** — **path-scoped** to `apps/web/src/{app,components,lib}/**` and `middleware.ts`. Framework baseline under `apps/web/CLAUDE.md`: thin `page.tsx`, `Link` for internal navigation, `params`/`searchParams` are awaited untrusted input, Server Components by default with `"use client"` at the smallest leaf, validate-and-authorise inside every Server Action and Route Handler, no secrets past `NEXT_PUBLIC_*`, stream with `loading.tsx`.

`.dependency-cruiser.cjs` enforces the interface-boundary rules at CI time. Run `pnpm dep-check` locally before pushing; it's a required CI step.

## CI

See `.github/workflows/ci.yml` for the job graph and `docs/ci-required-checks.md` for which checks branch protection requires (and which are deliberately advisory).

The split between the workflows is load-bearing: **`ci.yml` checks, `build-images.yml` publishes, and the two are connected by a gate rather than by `needs:`.**

- **`ci.yml`** — `pull_request` into `main`/`develop`/`feature` and `push` to `main`/`develop`. The `ci` job lints, type-checks, tests, builds, runs the OpenAPI spec-drift and dep-cruiser checks, and scans with SonarCloud. A second job, `smoke-image`, builds `api`, `web` and `worker` on the PR path with `push: false` — build only, because `server.ts` awaits `runMigrations()`, `getNetworkConfig()` and `loadEmailMessageOverrides()` at startup, so a boot probe would need Postgres, Redis and config fixtures and would go red for a missing service rather than a real defect. There is **no `feature` push trigger and no tag trigger** (#756): both existed only to drive the `docker` matrix, which no longer lives here.
- **`build-images.yml`** — publishes `api`, `web` and `worker` to GHCR on a **release tag** (`v*.*.*`, `20*-s*-rc*`, and the per-app `api-v*.*.*` / `web-v*.*.*` / `worker-v*.*.*`) or a manual run. No branch push publishes (#756). `:latest` is gone with the branch triggers — it was gated on `{{is_default_branch}}`, so it tracked the main branch rather than the last release, and nothing pins it.
- **`create-release.yml`** — the front door for cutting a release. Dispatch it with a tag name and a base branch (`base` is only for `v*.*.*`/extra tags. The `docs_only` input re-publishes an existing tag's notes to the docs PR.); it checks CI, creates the tag and the GitHub release with notes taken from the release PR sections (curated, not PR titles) in one API call, then dispatches the image build. `dry_run` previews the notes without creating anything. Its tag validation accepts the per-app prefixes as well as the org-wide patterns.
- **`keycloak-theme-build.yaml`** (dispatch-only, parameterised by network and brand) and **`openapi-sync.yml`** / **`security.yml`** are unrelated to the release path. Note `release.yml` was deleted: it ran changesets, had never executed once, and the repo's release tags were always cut by hand.

**The CI gate (Blue-Dots-Economy/signals-dpg#765).** Publishing used to be gated by `needs: ci` on the `docker` job. #756 moved publishing into its own workflow, and `needs:` cannot reach across workflows, so the dependency is now a lookup: both `build-images.yml`'s `verify-ci` job and `create-release.yml` query `ci.yml` runs for the commit and refuse unless one concluded `success`. Three things about it are deliberate and easy to undo by accident:

- It reads **workflow runs**, not check runs, so it stays correct if the job names or the job graph inside CI change.
- It **fails closed when there are zero runs**. That is the realistic accident (a tag on a commit CI never saw), not a tag on a commit CI rejected; a "did it fail?" test would wave it through.
- Both carry a `skip_ci_check` input for an emergency publish, which logs a warning naming the commit so the bypass is visible.

**Sprint tags come in three kinds, each cut from its own branch: candidate `YYYYMM-sN-rcN` from `develop`, release `YYYYMM-sN` from `main`, hotfix `YYYYMM-sN.M` from `release/YYYYMM-sN`. Never `feature`.** Cutting the release tag also creates `release/<sprint>`; hotfixes are PRs into that branch, and `sync-release-branch.yml` opens carry-back PRs into `develop` and `feature` (merge commit, not squash). `base` is only for `v*.*.*` and extra tags (default `main`; `develop` or `main`), sprint tags ignore it. Merges into `feature` run no CI — `pull_request` runs record the PR head, not the resulting merge commit — so the gate will refuse a tag cut there.

**Two GitHub behaviours the release path depends on**, both of which look like bugs when you hit them: a tag pushed with `GITHUB_TOKEN` does **not** trigger `on: push: tags` (GitHub suppresses it to prevent recursion), which is why `create-release.yml` creates the tag through the REST API and then dispatches the build explicitly; and a workflow is **not dispatchable until it exists on the default branch**, so `create-release.yml` will not appear in the Actions tab while it sits on a side branch.

## Authoring pull requests

Split a change into one PR per block and stack them, as `.claude/rules/pull-requests.md` sets out. When you open a PR, include an **In Plain Terms** section in the description: a short, jargon-free explanation a non-expert teammate can follow — what the problem was and what the change does, in everyday language — alongside the usual Summary / Release Notes. Skip it only for a pure chore with no behavioural effect. This lives here as a Claude authoring rule rather than in the GitHub PR template on purpose, so PRs opened from other tools/flows aren't forced through it. For release and promotion PRs, use the `release-pr-notes` skill from the `bluedots` plugin marketplace; it writes every release section, including Breaking changes / config and What users will notice.
